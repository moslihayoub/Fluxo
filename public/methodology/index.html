🏛️ 1. Architecture Globale & Carte du Codebase

Structure

L'application est architecturée autour de Next.js 14 (App Router) en mode Single Page Application (SPA / PWA) haute performance, orchestrée par un store Zustand unifié.

Arborescence Clé 
/src
  /app           ← layout.tsx (Providers & SEO), page.tsx (Routage SPA via Zustand), api/
  /components    ← Composants par domaine métier (auth, layout, operations, months, dashboard)
  /store         ← Zustand slices indépendants (operationsSlice, uiSlice, categoriesSlice...)
  /lib           ← Firebase.ts, Schemas.ts (Zod), Utils.ts (toCents/fromCents)
  /types         ← Définitions TypeScript globales
.spec            ← Spécifications fonctionnelles et techniques (Spec-Kit SDD)

🔀 2. Stratégie de Routage — Compromis Assumé (SPA-First)

Décision Architecturale
📌 Décision délibérée et assumée
Fluxo utilise un routage interne géré par l'état Zustand (activeView) plutôt que le routeur fichier de Next.js.
  • Pourquoi ? Expérience d'application mobile installée (PWA), transitions instantanées sans rechargement, gestion du retour natif.
  • Ce qu'on perd (assumé) : Pas d'URLs profondes directes ni de SEO par sous-vue. Les balises Open Graph et meta tags sont configurées à l'échelle globale de l'app.

💰 4. Intégrité des Données Financières — Règles Non-Négociables

Priorité Critique
⚠️ Règle Absolue : Zéro Float JavaScript
Les montants financiers ne sont JAMAIS stockés ni calculés en virgule flottante. Ils sont obligatoirement manipulés en centimes entiers (amount_cents: number).
src/lib/utils.ts (Conversion & Formatage) 
// Convertir une saisie utilisateur en centimes entiers
export function toCents(value: string | number): number {
  return Math.round(parseFloat(String(value)) * 100);
}

// Convertir des centimes entiers pour affichage formatté
export function fromCents(cents: number): string {
  return (cents / 100).toFixed(2);
}

Validation systématique Zod : Tous les flux de données (Firestore, formulaire, agent Gemini) doivent valider leurs entrées via .safeParse().

🗃️ 5. Architecture Zustand — Slices par Domaine

State Management

Pour prévenir le syndrome du "God Store", l'état applicatif est décomposé en slices spécialisés réunis dans useStore.ts :

  • operationsSlice.ts : Ajout, suppression, filtre des transactions
  • categoriesSlice.ts : Paramétrage des catégories
  • monthsSlice.ts : Gestion des clôtures comptables
  • uiSlice.ts : activeView, thème, état des tiroirs et modales

🎨 6. Cadrage & Audit UX/UI via uxspot MCP

Ergonomie

L'ergonomie et l'accessibilité sont vérifiées grâce aux outils MCP UXSpot :

  • Phase de Cadrage : Harmonisation du glossaire métier (search_glossary) et application des checklists mobiles (get_checklist).
  • Phase de Vérification : Respect des cibles tactiles minimales (44x44px sur mobile) et exécution d'audits contrastes WCAG (spot_check).

🛠️ 7. Protocole d'Implémentation d'une Fonctionnalité

Workflow
  1. Schéma Zod d'abord : Définir les types dans src/lib/schemas.ts.
  2. Slice Zustand : Créer ou mettre à jour l'état et les actions métier.
  3. Composants UI : Créer le dossier dédié dans src/components/[feature]/.
  4. Brancher la Vue : Conditionner le rendu dans app/page.tsx selon activeView.
  5. Navigation : Ajouter le déclencheur dans le Header.tsx.

📱 8. Méthodologie Responsive & Mobile-First

Design System
  • Mobile : Utilisation stricte de Bottom Sheets (tiroirs coulissants) et boutons d'action flottants (FAB).
  • Desktop (sm:) : Modales centrées avec backdrop flouté.
  • Écrans tactiles : Remplacer les hover: lourds par active: et désactiver les comportements non sollicités via select-none.

🤖 9. Sécurité de l'Agent IA (Gemini Finance Agent)

Zero-Trust
🛡️ Principe Zero-Trust
Toutes les réponses de l'agent IA sont considérées comme non fiables par défaut jusqu'à validation.
  • Pas d'écriture directe : L'agent ne touche jamais Firestore directement. Il passe par une API route qui vérifie l'authentification.
  • Validation Zod : Parsing strict par safeParse de tout JSON retourné.
  • Confirmation utilisateur : Validation explicite requise pour toute action de suppression ou de modification en masse.

⚡ 11. Normes de Performance, SEO & Sécurité

Robustesse
  • Médias & LCP : Images WebP/AVIF avec fetchpriority="high" au-dessus de la ligne de flottaison.
  • Résilience (Graceful Degradation) : Fallback localStorage ("Guest Mode") et gestion des erreurs réseau par toasts sans écran blanc.
  • Firestore Rules : Contrôle strict d'accès request.auth.uid == userId.

🚀 12. Protocole de Déploiement Strict

Contrôle Humain
🛑 Validation Humaine Obligatoire
Ne JAMAIS exécuter de commit/push Git ni déclencher de pipeline de déploiement (Vercel) sans l'accord explicite préalable de l'utilisateur.
  1. Smoke test de fin de tâche validé.
  2. Linter sans erreur : npm run lint.
  3. Build de production réussi en local : npm run build.
  4. Alerte proactive si la session de conversation devient longue (recommander une nouvelle session pour maintenir des performances optimales).
